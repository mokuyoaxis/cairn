# 长任务中的 Prompt 长度与经验注入：两组对照实验（2026-11）

> 类型：研究记录，不是产品功能说明，也不构成路线图承诺。
>
> 适用范围：Cairn v0.1.1 与一个 12 条种子加 33 条领域卡的实验库。
> 性质：合成/手工标注的工程实验，不是统计调查或宿主集成评测。

## 1. 研究问题

Cairn 的默认部署形态是编码 Agent、较短提示和十几条经验。当它被放进多步长任务（写综述、写实验方案、写专利交底书）时，调用方可能把整段任务书交给 recall。

本实验最初想验证经验注入对产出是否有用，却先观察到两个静默失效：

- 长查询可能一条都检不到；
- 库变大时注入率下降，但排序质量不一定同步下降。

调用方通常无法区分“库里没有”和“闸门没有放行”。

## 2. 实验口径

- 库：12 条种子库加 33 条领域经验卡（写作、交付、实验、专利），全部为 active + verified + source + verified_at 的合成条目；
- 评测集 A：现有 80 条正例和 60 条负例；
- 评测集 B：新写 22 条正例、15 条负例，按口语提问撰写，不复制卡片摘要；
- 任务实验：3 个写作任务，各配独立的确定性门禁（6 至 7 项），比较“整段任务书一次检索”和“三条短 query 分点检索”。

可证伪假设：

- H1：query 达到一定长度后，即使存在明显相关条目，cover 也会因分母是查询 token 总数而低于 20%，注入为 0。
- H2：仅增加库中卡数，会降低注入率，而排序质量（召回@3）不变；若注入率不降或召回同步下降，则否定“闸门变严”解释。
- H3：同一任务下，同一组相关卡“一起交付”比“全部沉默”在门禁上通过率更高。

## 3. 长查询结果

查询：你是一位科研写作助手。请基于 papers.json 中的 12 篇文献……（180 字）｜候选 20 条｜会注入 0 条

门限：score≥0.40，cover≥20%，margin≥1.50x，scope 未声明

- section-citation-minimum：norm=0.29，cover=4/88，low_score
- citation-claim-mapping：norm=0.21，cover=3/88，low_score
- prisma-number-reconciliation：norm=0.20，cover=3/88，low_score

同一任务改写成 3 条短 query（如“文献综述 交付 引用 检查”）后，每任务注入 5 张，其中 3 至 4 张与任务强相关；3 个任务 3/3 复现。

现有文档曾提醒“2-gram 分词对很短 query 较粗”，但长查询是相反方向的失效。

## 4. 库规模结果

| 库规模 | 召回@1 | 召回@3 | 注入@3 | 误触发 |
|---:|---:|---:|---:|---:|
| 12 条 | 93.8% | 100% | 72.5% | 3.3% |
| 24 条 | 93.8% | 100% | 70.0% | 6.7% |
| 45 条 | 88.8% | 100% | 65.0% | 5.0% |

45 条时自带评测 FAIL（注入@3 65% 低于 70% 门槛）。只调整 margin：

| min-margin | 注入@3 | 误触发 |
|---:|---:|---:|
| 1.5（默认） | 65.0% | 5.0% |
| 1.3 | 72.5% | 6.7% |
| 1.2 | 72.5% | 8.3% |
| 1.0 | 77.5% | 16.7% |

召回@3 恒为 100%，失败主要发生在闸门层：min_margin 是固定倍数，库越大近邻越多，top1 与 top2 越接近。

## 5. 同主题多卡对照

| 任务 | 整段任务书（注入 0 张） | 三条短 query（注入 5 张） |
|---|---|---|
| 文献综述 | 5/6，引用覆盖率 63% 未过 | 6/6，覆盖率达标 |
| 实验方案 | 6/7，表格无编号与正文引用 | 7/7，5 张表全部编号并引用 |
| 专利交底书 | 6/6 | 6/6 |
| 全通过 | 1/3 | 3/3 |

失败项恰好是被注入卡覆盖的那一项；第三任务模型本来就会，卡片为中性（无收益也无损害）。

## 6. 与相邻研究的关系

候选预算实验已经记录：同分合格同行存在时，目标可能因 low_margin 全部沉默；并明确没有测“多个相关条目是否应该一起交付”。本页补的是它留空的两点：

- 多个相关条目一起交付是否有可测收益；
- 在没有截断、不涉及不合格条目的干净库上，仅凭规模增长是否也会降低注入率。

候选数在这些库中远少于 20 的候选预算，因此不能用候选饥饿解释 H2 的结果。

## 7. 反例与边界

- 同主题多卡只有 3 个任务、每格 1 次，属于方向性证据，不是统计结论；
- 第三任务两组均通过，说明“一起交付”并非普遍有效；
- 卡片由实验作者按任务失败模式撰写，属于上限估计；未筛选的自然召回组与安慰剂组无差异（2/4 对 1/4，p=1.00）；
- 未测长会话、去重、多轮注入的累积效应，也未测其它模型；
- 合成库的 12/24/45 条规模不等于真实用户库分布。

## 8. 可执行建议

1. **文档**：在 recall / hook 用法处写明 query 的推荐长度；在 Known limitations 增加“长查询稀释 cover”和“库规模影响 margin”。
2. **运行时**：当 query token 数超过阈值时打印一行 warning，说明 cover 的分母口径。
3. **算法**：cover 可考虑改为“命中关键术语数 / 关键术语总数”的 IDF 加权形式；margin 可考虑随候选密度自适应，或对同 scope 的近似并列候选按“一组”处理。
4. **评测**：eval 增加“库规模”和“query 长度”两个维度，避免阈值只在单一分布上标定。

这些是研究方向，不是本页承诺的已实现能力。

## 9. 结论

本实验支持两个窄结论：

- 长任务提示中的大量无关 token 会稀释 query 的 cover，导致相关条目在分数/覆盖门上静默消失；
- 仅增加库规模会降低注入率，而召回@3 可以保持不变。

它不支持“所有长提示都无效”“库越大越差”或“调整 margin 没有代价”这类泛化结论。
