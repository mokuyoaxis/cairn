# Taxonomy v2 可行性研究总结（2026-10）

- 状态：**研究已归档（Research Archived）；内建适用性门控：NO-GO**
- 适用范围：本文是工程研究总结，不是论文；结论限于当前 Cairn 宿主契约
- 相关：`docs/architecture.md` §6、`eval/README.md`、`CHANGELOG.md`

## 1. 为什么研究这个

Cairn 注入的是「历史经验」，而历史经验最危险的地方不是找不到，是**用错**：
条件不同、版本不同、环境不同时，一条正确的经验会被当成当前问题的根因。
诊断学里有一整套现成结构处理这件事——症状、体征、综合征、鉴别诊断，
所以我们花四轮研究了「要不要把它搬进检索层」。

核心问题：**Cairn 能否在注入前判断「这条经验此刻适用吗」？**

## 2. 四轮做了什么

| 阶段 | 问题 | 主要做法 |
|---|---|---|
| Phase 1 | 分类学怎么设计 | 症状/体征/综合征/鉴别字段；12 条研究语料 + 23 条用例；A/B/C 对照 |
| Phase 2 | 适用性怎么真正生效 | 三值判定（applicable/inapplicable/unknown），事实由调用方声明；18 条独立用例 |
| Phase 3 | 过滤顺序与阈值的取舍 | 三种顺序（先 margin / 先适用性 / 扩池）× 六个 margin；24 条留出用例 |
| Phase 4 | 宿主到底能不能提供可信事实 | 审计真实入口；信任边界原型；端到端链路；核心补丁成本实测 |

全部实验均为**离线 harness**，`cairn.py` 四轮中**未被修改**。

## 3. 主要发现（含分子/分母）

实验环境：单机 Linux，Python 3.12（另用 3.9 跑过 AST 与 CI），12 条研究语料、65 条用例，
用例由同一作者构造，**不构成独立盲测**。

### 3.1 把「用户口语症状」作为检索面：初期看起来很好，复测变差

- Phase 1：16 条应命用例，交付覆盖 A 组 6% → B 组 69%；
- Phase 2 在**真实核心**里重测同一语料：top1 **13/14 → 11/14（变差）**，top3 13/14 → 14/14；
- 生产 80/60 回归集不受影响（示例库没有 symptoms 字段），所以「零回归」不等于「有收益」。

结论：症状字段改善的是**特定查询措辞**下的召回，代价是把 summary 与 symptoms 并权后稀释了领先幅度。

### 3.2 让卡片显式标注不确定：有效，但只作用于「已经注入」的样本

- 3 条需要标注的用例：B 组（无标注）**3/3 未标注**，C 组（有标注）**0/3 未标注**；
- 该指标的分母是「已注入次数」，A 组根本检索不到 → 分母为 0，**不能读作「A 更安全」**。

### 3.3 三值适用性（事实由调用方声明）：拦截有效，代价是过度沉默

- 不适用条目被当作适用建议交付：A/B/C 组 **8/11**，D 组（unknown 静默）**0/11**，D2 组（unknown 带标注）**2/11 且均带标注**；
- 召回不变（11/11、14/14）——安全**不是靠搜不到**换来的；
- 但总注入从 11 例降到 2 例（D）/ 5 例（D2）：**过度沉默是真实代价**。

### 3.4 过滤顺序：先适用性、后 margin，收益明确

24 条留出用例、margin=1.5、同语料同分数：

| 指标 | 先 margin（S1） | 先适用性（S2） |
|---|---|---|
| 正确行动性交付 | **2/9** | **7/9** |
| 过度沉默 | **7/9** | **2/9** |
| 不适用被交付 | 0/19 | 0/19 |
| 召回 | 16/16 | 16/16 |

设计反例成立：最高分候选（1.09 倍领先）已确证不适用，次高分适用但因 margin 1.09<1.5 无法交付；
S2 剔除前者后成功放行后者。

### 3.5 margin 扫描：降阈值买到的覆盖，要付泄露

- 0.5 / 1.0：两种顺序都出现 **2/19** 不适用条目被当作行动性建议；
- 1.2–2.0：S2 稳定 7/9 且 0 泄露；S1 在 1.2 以上只剩 2/9 交付。

### 3.6 诊断提示通道：共用 margin 会被饿死

3 条需要提示的用例：全静默 **0/3**、共用 margin **2/3**、独立通道 **3/3**；
独立通道同时满足「矛盾条目 0 提示」「无关查询 0 噪音」「每次 ≤1 条」。
**样本仅 3 条**，只能算可行性证据。

### 3.7 宿主能提供什么事实（Phase 4 审计）

全仓审计：Cairn 唯一的自动入口是 `hook`（stdin JSON 的 `prompt` 与 `session_id`），
没有 MCP、socket、HTTP 或子进程通道。因此可 `verified` 的只有**进程自身能观测**的事实：
OS、Python 版本、cwd。

而经验真正关心的前提——SQLite 的 `journal_mode`、`checkpointed`、执行脚本的 shell——
**核心看不到，也不应为此新增环境扫描能力**。

### 3.8 把「先过滤」搬进核心的真实成本

隔离原型实测：**+41 行**（1198 → 1239），208 项测试全绿，生产 80/60 基线逐项不变。
但同一原型**缺少事实信任层**时，不适用交付从 3 对涨到 **5 对**（自报覆盖实测、过期未失效、同级冲突被覆盖）。
补上信任层再加约 30~35 行，合计约 +76 行 —— 超出「核心 ≤1200 行」的预算。

## 4. 已纠正的错误与方法学局限

| # | 问题 | 处理 |
|---|---|---|
| 1 | 曾把 bash 手册中 `-n` 分支的退出码规则误读成裸 `wait` 的规则，并据此宣称「文档与实测冲突」 | 已勘误：文档与实测一致 |
| 2 | 曾把 `docker compose config --no-env-resolution` 的效果写成普遍结论 | 改为限定 Compose 2.40.3，并补测 `--no-interpolate` 等组合 |
| 3 | 3 条用例标注错误（自相矛盾的双标签、把相关条目误标为应沉默、漏标事实） | 逐条更正并记录 |
| 4 | 安全指标曾以「已注入次数」为分母，A 组分母为 0 却报 0% | 改为同时报告分子/分母，分母为 0 记「未定义」 |
| 5 | 门控规则在同一批用例上迭代多次，未留出独立集 | Phase 2/3 各自新增独立用例，并声明**非盲测** |
| 6 | Phase 2 的 harness 曾把「自报适用」渲染成普通卡片（无标注） | 改为三分类交付，并修正历史数字（2 条 → 1 条） |

## 5. 有收益但暂不集成的能力

| 能力 | 收益 | 为何暂不集成 |
|---|---|---|
| `symptoms` 检索面 | 特定措辞下召回提升 | 真实核心中 top1 下降；收益不稳 |
| 三值适用性门控 | 不适用交付 8/11 → 0/11 | 依赖宿主事实；核心集成 +76 行且需信任层 |
| 先适用性后 margin（S2） | 正确交付 2/9 → 7/9 | 没有事实就没有意义（无事实时 S1 与 S2 等价） |
| 独立诊断通道 | 提示命中 0/3 → 3/3 | 样本仅 3 条；与行动性建议的边界需重新设计 |
| `role`/`state` 字段 | 语义更清晰 | 需要 Schema 迁移，收益未被证明 |

## 6. 决策：NO-GO（当前宿主契约下）

**Research Archived — Built-in Applicability Gating: NO-GO under Current Host Contract.**

理由（不是「原理失败」）：

1. 适用性门控在隔离实验中确有价值；
2. S2 在特定测试集上改善了正确经验交付；
3. 真正有用的**可信项目级事实**当前宿主无法充分提供；
4. 不完整的事实信任层会引入安全回归；
5. 完整核心集成的收益与复杂度不匹配；
6. 独立诊断通道与症状索引增强尚未达到采纳标准。

因此：不迁移 `role`/`state`，不内建 `requires`/`excludes`，不内建诊断通道，不把 Cairn 扩展成环境扫描器。
离线代码保留在 `eval/` 供复现与审计，**其接口不是稳定公共 API**（见 `eval/README.md`）。

## 7. 什么条件下值得重新评估

1. 宿主能以**可信、只读**方式提供真正有价值的项目级事实；
2. 宿主侧已有成熟的事实判断能力，可经**明确协议**提供适用性结果；
3. 出现**真实使用数据**，证明现有 Cairn 存在值得用额外复杂度解决的适用性失败。

以上条件**尚未满足**，也不得按「可能会满足」提前设计。

## 8. Cairn 目前真正实现的功能边界

已实现（生产）：Markdown 条目库 + Experience Contract v0 准入 + 三道门 + 声明式 scope 过滤 +
卡片注入（≤3 条）+ `explain` 拒绝理由 + `lint`/`audit`/`import`/`sanitize`/`stats`/`nudge`。

未实现（研究或未采纳）：症状索引、`role`/`state`、事实上下文、适用性门控、诊断通道、
冲突检测、自动过期、反馈驱动的生命周期、Embedding/向量库、模型调用。

## 10. 这份研究没能回答的问题

- 语料仅 12 条、用例 65 条、单人构造：任何「比率」都只能当探索性观察；
- 没有真实宿主上的任务级收益数据（不知道注入这些卡片是否真的让 agent 少走弯路）；
- 冲突检测、状态迁移（supported → established → refuted）未实现；
- 大库（数百条以上）下的门槛行为未测。
