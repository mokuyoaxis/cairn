# 架构与设计取舍

本文解释 Cairn 为什么这样检索、这样注入，以及哪些设计是刻意不做的。命令用法见 [usage.md](usage.md)，评测方法见 [evaluation.md](evaluation.md)。

> Cairn 的目标不是“记住更多”，而是在正确的时刻提供少量、可追溯、适用、可撤回的经验。架构必须服务于这个窄目标。

## 0. 摘要

- **确定性优先**：中文 2-gram + 英文词元 + BM25 + 契约准入 + 三道门；不依赖模型判断。
- **卡片优先**：注入 name + summary + path，不默认注入全文。
- **运行时只读**：不执行条目、不自动写入、不发起网络请求。
- **存储简单**：Markdown 是唯一权威源；缓存可重建；没有手写索引。
- **当前重点**：Experience Contract v0 已实现；接下来是统一的 Recall/Explain 与 Trust & Applicability Eval；控制台暂缓。

### 0.1 关键决策

| 决策 | 理由 |
|---|---|
| 不维护手写 INDEX | 索引会漂移；缓存必须能从 Markdown 重建 |
| 不用向量/模型做默认检索 | 可解释、零依赖、本地优先；语义缺口需先被评测证明 |
| 检索与注入分离 | 每轮可检索，但只有过门条目才进入上下文 |
| 只注入卡片 | 控制上下文成本，降低注入面 |
| Prompt-time Recall 为默认 | 在用户提问时提供经验；Decision-time Recall 为长期方向 |
| 经验不是指令 | 宿主权限与安全边界不由 Cairn 承担 |

## 1. 目标与非目标

**目标**

- 在用户提问的瞬间，自动给出少量相关经验；
- 检索与门控可解释、可复现；
- 本地优先、零第三方依赖、默认零网络；
- 运行时只读，不修改经验资产；
- 保持单文件核心、小到可以完整读一遍。

**非目标**

- 通用 RAG 服务、向量数据库；
- 完整会话记忆、Agent 编排；
- 自动生成/改写经验；
- 多平台 adapter 矩阵；
- 多租户或 Web 写入后台。

## 2. 主链路

```text
User Prompt
    |
    v
Hook Adapter（stdin JSON）
    |
    v
Prompt 提取 / 规范化
    |
    v
本地检索（2-gram + BM25）
    |
    v
Experience Contract 准入（active + verified + source + verified_at）
    |
    v
三道门（分数 / 覆盖率 / 领先幅度）
    |
    v
会话去抖
    |
    v
卡片渲染（名字 + summary + 路径）
    |
    v
Agent Context
```

管理链路是旁路：`add / import / lint / audit / sanitize / eval / stats`。它们可以修改数据，但不参与 Hook 的实时检索。

## 3. 存储：Markdown 是唯一权威源

- 条目就是 `$CAIRN_HOME/entries/*.md`；
- 没有需要人工维护的 `INDEX.md`；
- `cairn ls --md` 只是从条目实时生成的视图，不是运行时索引；
- `cache/index.pkl` 是派生缓存，可以随时删除并从 Markdown 全量重建。

这样做的原因：索引文件一旦需要手写/手同步，就会漂移；漂移后的索引会“告诉检索层有条目”，但实际正文已经变了。Cairn 选择让索引成为缓存，而不是资产。

缓存失效判据是所有条目文件的 `(文件名, mtime_ns, size)`。编辑器原地保存不会改目录 mtime，所以不能只看目录时间。

## 4. 分词

- 中文连续段按 **2-gram** 切分：`一直卡死` → `一直`、`直卡`、`卡死`；
- 单个汉字保留为单字 token；
- 英文/数字按连续词切分并转小写；允许 `.`、`_`、`-`；
- 去除低信息量中文 2-gram（如 `这个`、`可以`、`问题`）。

选择 2-gram 的原因：中文没有词边界，零依赖下 2-gram 是最稳的近似；它比纯子串匹配多了可加权、可排序的能力。

已知代价：单字词只能整词命中；同义词（`密码` vs `密钥`）不会自动等价，需要别名表。

## 5. BM25 打分

每个条目被拆成三个字段的 token 计数：

| 字段 | 权重 | 理由 |
|---|---|---|
| `summary` | ×3 | 作者已经做过摘要，噪声最小，也是主要检索面 |
| `name` | ×2 | 稳定的语义标识 |
| `body` | ×1 | 上下文补充，但噪声更大 |

BM25 参数：`k1=1.2`、`b=0.75`。字段权重体现在词频 `tf` 上，而不是分别建三个索引。

归一化分数：

```text
norm = score / Σ idf(query 中在库里真实存在的词)
```

分母只算**库内存在的词**：库外词无法被任何条目覆盖，算进分母会系统性压低长 query 的分数。`norm` 回答的是“这条 query 的信息有多少被该条目覆盖”，因此阈值可以跨库规模复用。

查询 token 会先去重、按 idf 从高到低排序，并截断到 80 个，控制长 query 成本。

## 6. 契约准入 + 三道门

Experience Contract v0 是注入前的硬准入，不参与排序：

| 条件 | 说明 |
|---|---|
| `status: active` | deprecated/archived 不自动注入 |
| `trust: verified` | unverified/quarantined 不自动注入 |
| `source` 非空 | 来源可追溯 |
| `verified_at: YYYY-MM-DD` | 有验证时间声明 |

排序结果先过滤掉不满足契约的条目；若调用方声明了上下文 `scope`，再剔除 `scope`
无交集的条目（`out_of_scope`）；最后应用三道门。契约不满足的条目仍可被
`recall --raw` / `show` 查看，但不会进入 Hook。`verified` 是自我声明，不是证明。

三道门默认参数：

| 门 | 默认值 | 作用 |
|---|---|---|
| 归一化分数 | `≥ 0.40` | 过滤整体不相关 |
| query 覆盖率 | `≥ 20%` | 挡住“只撞上一个泛词” |
| 领先幅度 | `top1 ≥ 1.5 × top2` | 两个条目都像时宁可不注入 |

领先幅度只在存在第二名时生效；只有一个候选时不会因为“没有第二名”而拒绝。

三道门都作用在排序结果上，不依赖库规模。它们的目标不是“尽量多注入”，而是“宁可沉默，也不要用错误经验污染上下文”。

> 这些阈值是手工定的，换库需要重调；`calibrate` 尚未实现。见 [evaluation.md](evaluation.md)。

## 7. 卡片渲染

注入的不是全文，而是卡片：

```text
【cairn】可能有用的既往经验（按相关度排序）：
- <name>：<summary> → entries/<name>.md
需要全文用 `cairn show <name>`；都不相关就忽略本提示。
```

约束：

- 默认最多 3 张；
- 总字符预算约 520；
- 超长行会截断；
- 无命中时不输出正文；
- 卡片带路径，Agent 需要时自己 `show` 全文。

这样做的原因：全文注入会把上下文成本从“几十 token”推到“几百到几千 token”，且大多数时候只需要知道“有没有这条经验”。

## 8. 会话去抖

同一会话同一张卡片只注入一次。会话标识优先取 Hook stdin 的 `session_id`，否则用 `CAIRN_SESSION`，再否则 `default`。

会话文件存放在 `log/session-*.json`，默认 12 小时后视为过期。去抖的目标是避免长会话里反复注入同一张卡片，而不是做完整的会话记忆。

未来需要重新审视：上下文压缩、会话恢复、子 Agent 独立上下文，都可能需要“重新注入”而不是永久去抖。

## 9. 失败语义

Cairn 区分两种失败：

- **Hook 检索增强：fail-open**  
  检索出错、索引损坏、stdin 不是 JSON：静默返回 0，不阻断用户任务，不注入不可信内容。
- **管理/写入/安全操作：fail-closed**  
  路径验证、数据校验、脱敏、原子写入失败时，不允许假装成功继续。

这也是为什么 `hook` 的异常处理和管理命令的退出码不同。

## 10. 为什么不默认用向量库

不是“反对向量”，而是当前阶段不划算：

- 引入 embedding 需要模型/服务、网络或本地模型依赖；
- 相似度分数不天然可解释，门控更难调；
- 个人/小团队经验库通常在几十到几千条，确定性检索已足够；
- 先证明确定性基线在独立评测集上有稳定的语义缺口，再谈可选后端。

如果未来引入，它应该是**可选检索后端**，而不是默认运行依赖。

## 11. 约束

- 核心 `cairn.py` ≤1200 行；当前 1198；
- 单文件核心；控制台/旁路必须独立模块；
- 零第三方依赖、默认零网络；
- Python 3.9+；
- Markdown 可被人类直接读、git、grep。

任何增加依赖、数据库或新子系统的改动，都必须回答：解决了什么实测问题、原方案为什么不足、增加多少运行/维护/安全成本。无法证明收益的复杂性暂缓。

## 12. 尚待研究

- 领先幅度门是否误伤“多个都相关”的场景；
- scope 目前只在**显式声明**（`--scope` / `CAIRN_SCOPE`）时门控；
  从 query 自动推断 scope 属于触发词工程，明确不做；
- 同义词/别名表；
- 不同库规模下的阈值校准；
- 上下文压缩后的重新注入；
- Explain 是否需要稳定的机器可读输出（JSON）供上层消费。

## 13. Recall 时机与契约边界

- **Prompt-time Recall 是当前默认实现**：用户提问时检索，过门后注入卡片。
- **Decision-time Recall 是长期方向**：在 Agent 决定下一步之前提供经验；暂不新增 Hook、平台矩阵或新的运行时入口。
- Recall 与 Explain 已共用同一套候选、分数、覆盖率、门控与拒绝理由；Explain 只读，不改变正常 Hook 行为。
- Experience Contract v0 已实现：来源、验证时间、生命周期、信任状态可表达；
  自动注入要求 `active + verified + source + verified_at`，导入默认 quarantine。
- `cairn explain "<query>"` 输出逐条 `[INJECT]` / `ineligible` / `low_score` /
  `low_cover` / `low_margin` / `over_limit` 与 `[SILENT]`，不写日志、不消耗会话去重。

## 14. 产品边界

Cairn 是 Local-first Experience Retrieval Layer，不是通用 Memory、自动 Skill 生成器或 Markdown 知识管理平台。  
存储可以继续用 Markdown，但文件树不是产品界面；默认交互应是搜索/召回卡片，而不是浏览目录。
